Screen 8 — Login / Sign Up · UX notes

  1. This screen appears only between Review and Payment. Everything before it — dates, travellers, destination, stay, room, services, traveller details and the total — is done as a guest.
  2. The banner states why sign-in is being asked for and shows the saved booking as chips, so the step reads as a checkout formality rather than a wall. Back to review is available without signing in.
  3. OTP login is offered at equal weight to the password, since a forgotten password is the most common blocker for this audience. It expands in place.
  4. After login or signup the user is returned straight to Payment with every selection intact; reached from the header instead, the same screen lands on the home page.

Screen 4 — Available Stays · UX notes

  1. The result count states the filter that produced it — group size and dates — and says how many properties were hidden for having no free rooms, so the list is understood as availability, not a catalogue.
  2. Traveller needs is its own tinted filter block; for a group containing a senior citizen it is pre-checked from step 2 rather than left for the user to find.
  3. Each card carries two prices: per night, and the estimated total for the chosen nights and the number of rooms this group needs. The estimate is what people actually compare.
  4. "Fits your group" states which room types work, so a group of four is not shown a two-person room as if it were an option.
  5. The trip bar is sticky and edits into a draft: nothing changes until Update Search is pressed, so a half-changed search never refreshes the list underneath. Committing it re-checks availability, and if a room was already chosen it is released with a warning rather than silently carried forward.
  6. Changing destination clears the stay, room and any services from the previous town, because services are destination-specific. The warning names what was removed.
  7. On tablet and mobile the bar collapses to one line — destination, dates, travellers, rooms — with the Modify button opening the same editor panel shown here.

Screen 5 — Stay Details + Room Selection · UX notes

  1. Every room row does the arithmetic in words — rate × nights — and states whether it fits the group in one room or needs two. The user never multiplies anything themselves.
  2. Senior-friendly details are a fixed table with concrete answers per property, so a lift-less dharamshala says so plainly rather than being silently unsuitable.
  3. The right panel is the same running summary as the previous step, now with a room line. It stays empty and honest until a room is chosen: Continue is disabled with the reason stated.
  4. Amenities show what the property does not have as well as what it does — absence is the deciding factor for elders.

Screen 6 — Optional Services · UX notes

Screen 8 — Review Booking · UX notes

  1. Six Edit actions, one per decision the user made: destination, dates, travellers, stay, room, services, traveller details. Each returns to the step that owns it with everything else intact.
  2. The price breakdown is built from the three sources the user chose — stay, services, taxes — in the same order and wording used on every earlier screen, so the total is recognisable rather than newly asserted.
  3. Two separate acknowledgements: refunds and terms. Refund expectations cause most support calls in travel.
  4. The stay row repeats the rate × nights × rooms arithmetic instead of only the result.
  5. This is the first point where an account is needed. Proceed to Payment signs the user in if they are a guest, then returns them to payment with the booking untouched.
